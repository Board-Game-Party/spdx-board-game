## จุดคอขวดของระบบที่ตรวจพบ (System Bottlenecks)

### 1. ระบบคำนวณคะแนนของทั้งคลาสใหม่ทุกครั้งที่ถูกเรียกดู
**ข้อมูลจากโค้ด:** ฟังก์ชัน `run_scoring_engine_for_assignment()` มีการดึงข้อมูลการจับคู่และผลประเมินของทั้งคลาสขึ้นมาคำนวณใหม่เสมอ โดยไม่มีการทำ Cache หรือเก็บบันทึกผลลัพธ์ลงตาราง
**ผลกระทบ:** ภาระงานต่อ 1 คำสั่งประมวลผล จะแปรผันตามจำนวนคู่ประเมินทั้งหมดในคลาสนั้นๆ หมายความว่าหากนักศึกษา 100 คนเปิดดูคะแนนตัวเองพร้อมกัน ระบบจะต้องคำนวณข้อมูลของทั้งคลาสใหม่ซ้ำถึง 100 รอบ แทนที่จะคำนวณเฉพาะข้อมูลของบุคคลนั้น

### 2. ไม่มีระบบปฏิเสธคำขอเมื่อโหลดเกินกำลัง (No Load Shedding)
ไม่มีการจำกัดอัตราการเรียก (Rate limit) และไม่มีการกำหนดความยาวคิวงาน ส่งผลให้เมื่อมีคำขอมากเกินกว่าที่เซิร์ฟเวอร์จะรับได้ คำขอเหล่านั้นจะค้างอยู่ในระบบจนถึงเวลา Timeout ผู้ใช้งานจะพบอาการหน้าจอค้างหรือ Error 500 (ระบบขัดข้อง) แทนที่จะได้รับการตอบสนองด้วยสถานะ 429 Too Many Requests เพื่อแจ้งเตือนให้ผู้ใช้งาน "ลองใหม่อีกครั้ง" ในภายหลัง การไม่มีระบบปฏิเสธที่ดีทำให้การกู้คืนระบบทำได้ยากขึ้นและให้ประสบการณ์ผู้ใช้ที่ไม่ดี

### 3. คอขวดจากการเขียนฐานข้อมูล (Database Locking)
ในการทดสอบ stress test พบว่า `POST /evaluations:submit` มีค่าเวลาตอบสนองโดยเฉลี่ย 3.2 วินาที แต่ค่า p99 กลับพุ่งสูงถึง **59.1 วินาที** (ห่างกันเกือบ 20 เท่า) ตัวเลขที่กระโดดห่างกันเช่นนี้คือรูปแบบที่ชัดเจนของปัญหา Database Locking จากการใช้ SQLite ไฟล์เดียว อย่างไรก็ตาม ข้อนี้อาจเป็นเพียงข้อจำกัดของสภาพแวดล้อมทดสอบ จำเป็นต้องทดสอบบน PostgreSQL ก่อนสรุปผล
